4. Tables#

How tables are stored, in Pages, Keynote and Numbers alike: the table model, its tiles and cells, cell formats, formulas and merged cells. How a Numbers document reaches its tables from the root is in Numbers, and Numbers' categories, filters and highlighting are there too. Every finding links to the experiments that support it, with a confidence level as defined in CONTRIBUTING.md. Records, object IDs and types are as described in 1. Container.

From the text to the table#

For a table, the attachment (type 2003, in Document.iwa) points at a drawable (type 6000, in CalculationEngine). The drawable holds the position and size in points (fields 1.1.1 and 1.1.2) and points at the table model (type 6001), whose fields 6, 7 and 8 are the number of rows, the number of columns and the table's name, and fields 9, 10 and 11 the numbers of header rows, header columns and footer rows (absent means 0; footer rows count within the rows, 0184), field 12 whether header rows are frozen (0125; fields 9 to 12 confirmed by writing them, 0301) and field 13 whether header columns are (0183; confirmed by writing it, 0401); field 29 is 1 when header rows repeat on each page (0246; confirmed by writing it both ways, 0402). Rows, columns and name are confirmed (0120, 0122, 0123). A Numbers table's stored y is 28 points less than the y Numbers reports (0126): the stored position is the corner of the whole object, and while the table's name is shown above it (model field 22), the body starts 28 points lower; with the name hidden the two are the same (confirmed by writing them, 0418). Sorting rewrites the rows (0119), and so does transposing, which also swaps fields 6 and 7 (0182). Likely (0020, 0060). A table's size is the sum of its row heights and column widths. The drawable's size can be out of date (0059).

The table model's storage#

The table model's field 4 holds its storage: 4.3 lists the tiles, each entry giving a tile index (4.3.1.1) and the tile record (4.3.1.2), and 4.1 and 4.2 name the row and column header storage buckets (type 6006). A bucket lists rows or columns with their own size in its repeated field 2: field 1 is the index, from 0, and field 2 the height or width in points as a float; unlisted rows and columns have the default size (0045; confirmed by writing them, 0308). Each tile covers 256 rows (field 4.3.2), and row numbers inside a tile are local, so a cell's row in the table is the tile index × 256 plus its row in the tile. A tile's field 4 counts its rows with content, but Numbers reads the rows from the field-5 entries themselves and ignores the count, and field 6, which held the same number (confirmed by writing wrong counts, 0437). Likely (0029, 0030), in Pages and Numbers alike. The row rule is confirmed (0030, 0063). Tiles without content are left out of the list, so a reader must use each entry's tile index. Likely (0063)

Rows in a tile#

A table's cells are stored by row in its tile (type 6002, Index/Tables/Tile.iwa). Each row with content is one field-5 entry: 5.1 is the row index, 5.4 a table of 255 little-endian 16-bit offsets into the row's cell bytes (one per column, ffff for an empty cell), and 5.6 the cell bytes. A cell starts with a version byte (5) and a type byte: 2 for a number, stored as a little-endian IEEE 754 decimal128, and 3 for text, stored as a 32-bit key into a string table (type 6005, Index/Tables/DataList.iwa) whose entries hold the key in field 3.1, the number of cells using it in 3.2 and the string, as UTF-8, in 3.3 (0113, 0118). Equal texts share an entry, so changing an entry's string changes every cell using it (confirmed by writing it, 0306), and unused entries are removed (0114), and long texts are stored whole (0130). Confirmed (0021, 0026); all three apps store the same cells byte for byte, and keep formulas, merges and header counts the same way (0131–0137).

When a row has several cells, it is field 5.7, not 5.4, that holds their byte offsets. Likely (0031)

Cells#

A cell's bytes 8–11 are little-endian flags saying which values and keys follow, in order of their bits. Further type bytes are 0 (no value, formatting only, 0138), 5 (date), 6 (boolean), 8 (a formula whose result is an error, stored with no value, 0078) and 10 (currency). Likely (0031)

Formats#

The format list's entries give the kind of format in field 1, which decides how the cells using it are shown (confirmed by writing 258 over 256, 0307, and 259 and 267 in a sweep of kinds, 0323) (256 number, 257 currency, 258 percent, 259 scientific, 260 text, 261 date, 262 fraction, 263 checkbox, 267 rating, 268 duration, 269 numeral system (0181), whose field 8 is probably the base), plus its details, such as a currency code or a date pattern: field 2 is the number of decimal places, 253 for automatic (0341), field 4 the negative style (0 minus sign, 1 red without a sign, 2 in parentheses, 3 red in parentheses, confirmed in 0343) and field 5 the thousands separator (0342); for a currency, field 3 is the ISO 4217 code (confirmed by writing them, 0339); for a date, field 14 is the pattern in Unicode date-pattern syntax, such as dd.MM.y HH:mm (confirmed, 0340). A formula cell also keeps its last result as a value, as a cell of the result's type: a date, or text through the string table (0108, 0110). Writing a new decimal128 in place of a cell's value changes the cell, so nothing else caches it (0290). A negative decimal128 has its sign bit set, confirmed (0112, 0174). Text that looks like a number is stored as a number unless the cell's format is text (0176). Likely (0031)

Formulas#

A SUM node also ends a merged range (0044). Numbers up to 167 follow the functions' English names alphabetically, with SUM (168) the exception, and 169 to 184 are the operators; later functions have higher numbers, up to 391. Every number's function is in [recipes/0316-functions.tsv](../recipes/0316-functions.tsv), read from Numbers itself (confirmed, 0316). More are listed in 0223 (44) and 0248 (70), apart from its TIME row, which was the Norwegian TIME, that is HOUR (60); English TIME is 152. Function names aren't stored, and formulas set through AppleScript are parsed in the app's language (0265).

Merged cells#

Merged cells are recorded in the table model's field 47.2, as ranges in this node form, not in the cells. In each range's first node, field 40.3 is the span of columns and 40.4 the span of rows, each { 1: first, 2: last } counted from 0, with a missing last meaning a span of one: 40.3 = { 1: 2 } and 40.4 = { 1: 1, 2: 2 } is C2:C3 (confirmed by writing them, 0382). A merged cell keeps its value in its top-left cell. Likely (0044). Numbers also shows a value stored in another cell of the range when the top-left is empty, and gives the merged cell the top-left cell's look (confirmed by writing it, 0426).
