Features and scope#

This page says what full support for Pages, Numbers and Keynote documents means, which smaller profiles measure progress towards it, and which features exist. Each feature has one issue that owns its research. The coverage columns of the inventory are worked out from the experiments each feature cites, so they say what has been shown, not what an issue's closed state might suggest.

Capabilities#

An application can do six things with a feature. Each one is tested on its own, for each app.

CapabilityAn application that has it canShown by
ReadFind the feature in a document an app saved, and get its values and meaningAn experiment that changes the feature in the app and records where and how it is stored
EditChange the feature in a document an app saved, so that the app opens it and shows the changeAn experiment that changes the stored values with the project's writer and checks the result in the app
CreateWrite the feature into a document made without any document an app saved, so that the app opens it and shows the featureAn experiment that builds the document from nothing; none has yet (#4, #27, #35)
RenderDraw the feature as the app draws itA comparison of an independent drawing with the app's own; none has been made yet
CalculateWork out the values the app works out: formula results, pivot summaries, highlighting and filter resultsAn experiment comparing computed values with the app's; for features whose Also column names it
PlayRun the feature in a presentation as Keynote does: builds, transitions, sound, movies and timingAn experiment comparing playback with Keynote's; for features whose Also column names it

Saving is not a capability of a single feature: it is the container features below (package, chunks, references, data files, password protection), at the edit or create level, together with the rules for what must be kept or changed when saving (#6).

Profiles#

A profile is a capability across every feature of one app. They measure progress; none of them is full support.

  • Read profile: read for every feature the app has. A reader with it can get all of a document's content and settings, though not draw them.
  • Render profile (and calculate for Numbers, play for Keynote): the read profile, plus render (and calculate or play) for every feature that has them.
  • Edit profile: edit for every feature, and saving a changed document so that every part the application didn't change survives.
  • Create profile: create for every feature, starting with the smallest document each app opens.
  • Full support for an app is all of its profiles together, in every release in scope.

A feature counts towards a profile in an app only when its state for that capability is shown. Shown means at least one experiment shows the capability for some of the feature: it is the evidence a reader can start from, not a claim that the feature is complete. Its owning issue lists what is left.

States#

The inventory gives each capability of each feature one of four states for each app:

StateMeans
ShownA cited experiment ran in that app and shows the capability for at least part of the feature. The release it ran with is listed with it
Not testedThe app has the feature, and nothing has shown the capability there yet
Not checkedThe feature is listed for the app with a question mark: whether the app has it at all has not been checked in its interface yet
Doesn't applyThe app doesn't have the feature, as its interface shows; Numbers has no footnotes, for example

A field seen in files whose meaning isn't known is not a state of the feature: the chapter that describes it marks it unknown (see CONTRIBUTING.md), and the feature's owner keeps it open. The confidence levels in the chapters and the states here answer different questions: a chapter says how sure a statement is, the inventory says which apps and capabilities have any evidence at all.

How the coverage is worked out#

The site's builder reads the inventory below and, for each cited experiment, the app and release rows of its setup. An experiment counts for each app its setup names. It counts as edit evidence when it wrote the document with the project's writer (its setup has a Writer row, or its name begins with writing) and as read evidence otherwise. An evidence entry can name another capability before the number, such as create 0480, once an experiment shows one. An experiment run with the tool alone, such as a regression check, is linked but counts for no app.

The builder stops when a feature cites an experiment that ran in an app its Apps column leaves out, so the applicability and the evidence can't disagree. It also writes the inventory, with every state spelled out, to features.json. Each feature there has these fields, which stay stable:

FieldHolds
idThe feature's ID, area.name. An ID never changes or gets reused; a feature that is split keeps its ID for one part
featureIts name
owner, owner_urlThe number and address of the one issue that owns its research
spec, pageWhere the specification describes it, and its row on this page
formatsFor Pages, Numbers and Keynote: applies (yes, unverified or no), the releases its evidence ran with, and for each capability its state and evidence
experimentsEvery experiment the feature cites

Releases and producers#

The specification describes the format as the newest apps write it, Pages, Numbers and Keynote 16.0 for macOS. Most of the evidence comes from 15.4, which writes the same format; the releases page says how 16.0, 14.5 and 13.1 were checked against it and what differs. The releases each feature's evidence ran with are shown with its states.

Producer or releaseScopeWhy
Pages, Numbers and Keynote 16.0 for macOSCurrentThe release the specification describes. It opens, draws and saves the 15.4 samples as 15.4 wrote them (0470, 0471, 0476), and makes new ones with the same structure (0473)

A statement that doesn't hold for every release checked carries a version note where it stands; the releases page gathers them.

Closing a feature issue#

An issue that owns features can close when, for each feature it owns and each app that has it:

  1. Every capability the feature has is shown in the current release, or in 15.4, with experiments cited in the inventory, or the gap is moved to another open issue that the inventory then names as its owner.
  2. Every not checked entry has been checked in the app's interface and changed to the app or removed.
  3. The chapter describing the feature states its rules with a confidence level, and nothing it relies on is left unknown without an open issue to settle it.
  4. Older releases are shown, or left to #23 explicitly.

Closing an issue finishes a piece of research; it doesn't mean the format is fully supported. Full support for an app is reached only when every feature in its column is shown for every capability it has, which the summary table shows directly. An audit that finds a gap links it to an open owner; it doesn't declare it out of scope.

Keeping the inventory up to date#

  • A new experiment is added to the Evidence column of each feature it shows something about. The coverage follows by itself.
  • A feature found in an app's interface gets a new row, with a new ID and one owner. When research splits a feature, its ID stays with one part and the other parts get new IDs.
  • When an issue is split or its scope moves, the Owner column changes with it, and the roadmaps (#24 for Numbers, #25 for Keynote, #26 for Pages) list the same issues as owners. The owners here are where to look first.
  • Applicability comes from what the apps' interfaces offer, never from the names of fields. An app listed with a question mark hasn't been checked yet.
