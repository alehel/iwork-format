Reading a Pages document#

This page follows one file from its ZIP listing down to the five bytes that hold its text. The file is hello.pages: a new blank document in which the word hello was typed and saved (0002).

1. The ZIP package#

A .pages file is a ZIP archive whose entries are stored, not compressed (container.md). This one holds 13 parts:

hello.pages: ZIP file, 13 parts
        size       stored  name
          23           23  Index/AnnotationAuthorStorage-1732609.iwa
         542          542  Index/CalculationEngine-1732610.iwa
        7690         7690  Index/Document.iwa
          77           77  Index/DocumentMetadata.iwa
       45708        45708  Index/DocumentStylesheet.iwa
       16883        16883  Index/Metadata.iwa
         723          723  Index/ViewState.iwa
         271          271  Metadata/BuildVersionHistory.plist
          36           36  Metadata/DocumentIdentifier
         525          525  Metadata/Properties.plist
         838          838  preview-micro.jpg
        1479         1479  preview-web.jpg
       13885        13885  preview.jpg
PartHolds
Index/*.iwaThe document's objects. Most of this page is about these.
Metadata/Properties.plistA binary property list: UUIDs, file format version, flags
Metadata/DocumentIdentifierThe document's UUID, 36 ASCII characters
Metadata/BuildVersionHistory.plistThe template and the Pages build that wrote the file
preview*.jpgPreviews of the first page, which readers may ignore

A name ending in a number, such as CalculationEngine-1732610.iwa, carries the ID of the part's first object. Names can change when a document is saved again, so a reader should list the parts rather than expect fixed names.

2. Chunks#

The text lives in Index/Document.iwa. An .iwa part is a series of chunks, each with a four-byte header: a type byte, always 0, then the length of the chunk's data as a 24-bit little-endian number (container.md). This part has one chunk:

Index/Document.iwa: 1 chunk, 7690 stored bytes, 14155 decoded bytes
    offset  type     stored    decoded decoded at
         0     0       7686      14155          0

These are the first bytes of the part as stored:

00000000  00 06 1e 00 cb 6e 68 56 08 01 12 52 08 90 4e 12  |.....nhV...R..N.|
00000010  03 01 00 05 18 f6 0a 22 07 0a 03 0a 01 2e 18 01  |......."........|
00000020  22 09 01 09 f4 48 01 2f 10 01 18 01 22 0b 0a 05  |"....H./...."...|
BytesMeaning
00Chunk type 0
06 1e 00Length 0x001e06 = 7,686 bytes of chunk data follow
cb 6eStart of the chunk data, a raw Snappy block: its decoded length as a varint, 0x4b + (0x6e × 128) = 14,155
68A Snappy literal tag: 0x68 >> 2 = 26, so 27 literal bytes follow
56 08 01 12 52 …Those literal bytes: the start of the decoded data

Snappy is Google's public compression format; the chunk data is a raw block, without the framing format's stream header. Each chunk decodes to at most 65,536 bytes, and a part's decoded chunks are joined end to end.

So the payload is the 1,398 bytes after the header, at offset 1 + 86 = 87, as the records listing shows. Field 2 can repeat when a record has more than one payload; the payloads then follow each other (container.md).

4. The document root#

Object 1 is the root of a Pages document. Its payload is another Protocol Buffers message. Without a schema, a reader sees only field numbers and wire types; the specification gives them meaning. These are some of its fields:

Floats are stored as 32-bit fixed-width fields, which iwork-probe shows both as integers and as floats. A reference is always a small message whose field 1 is an ID; every ID referenced this way is also listed in the record's header, which is how a reader can walk from the roots to every object without understanding each type (container.md).

5. The body text#

Following root field 4 leads to object 1732539, a record of type 2001: a text storage. Its payload starts with these bytes:

00002e72  08 00 12 04 08 85 e0 69 1a 05 68 65 6c 6c 6f 2a  |.......i..hello*|

1: varint 0
2: message (4 bytes)
  1: varint 1732613
3: text (5 bytes) "hello"
5: message (10 bytes)
  1: message (8 bytes)

  1: message (8 bytes)

The text has no terminator; the field's length is the text's length in bytes (text.md). Paragraphs are separated by U+000A. The fields after 3 are run tables: each lists positions in the text, in UTF-16 code units (text.md), and what applies from there on. Field 5 is the paragraph runs: one entry at position 0 naming paragraph style 1731511.

iwork-probe text does all of this in one step:

== Index/Document.iwa object 1732539 (field 1 = 0)
hello

6. The paragraph style#

Object 1731511 is in Index/DocumentStylesheet.iwa. It is a type-2022 paragraph style:

1: message (49 bytes)
  1: text (10 bytes) "Brødtekst"
  2: text (29 bytes) "text-20-paragraphstyle-Body 1"
  5: message (4 bytes)
    1: varint 1732613
10: varint 57
11: message (181 bytes)
  1: varint 0
…

Field 1.1 is the style's name, as the app's language shows it (Brødtekst is Norwegian for Body, since this document was made in Norwegian) and 1.2 its identifier, which doesn't depend on the language. Field 11 holds its character properties and field 12 its paragraph properties. Styles inherit from a parent, and a property missing from a style comes from the parent (text.md).

What was skipped#

This walk-through followed one path. The same steps lead everywhere else: list the parts, decode the chunks, read the records, and follow references from objects 1, 2 and 71. The remaining 51 records in Document.iwa hold header and footer texts, the section, the document settings and more, each described in the specification.
