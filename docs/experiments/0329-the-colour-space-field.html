0329: The colour space field#

App release: 15.4

Status: run

Colour messages hold red, green and blue in fields 3, 4 and 5, which matched sRGB in five colours (0309, 0328), and also have a field 12, always 1 so far. This experiment writes other values of field 12 into a page background and measures the colour drawn.

Setup#

Pages15.4
macOS26.5.2 (25F84)
Date2026-11-10
Inputsamples/0328/background.pages: a page background of 0.6, 0.8, 1.0, without field 12
Writerrecipes/0302-set-path.py

Recipe#

mkdir -p samples/0329
for v in 0 1 2 3; do
  python3 -I recipes/0302-set-path.py samples/0328/background.pages samples/0329/space$v.pages 1732296 30.1.12 varint $v
done

Pages opened each file on its own and exported it as PDF; each page was drawn and its corner pixel read in sRGB. The same components read as Display P3 were converted to sRGB with macOS's colour conversion, for comparison.

0.6, 0.8, 1.0 in Display P3 is 0.541, 0.807, 1.000 in sRGB.

Corrected 2026-11-25: space1.pages is byte for byte 0328/background.pages, so field 12 = 1 was never written here, and the row for 1 is the row for absent again. That 1 is sRGB rests on the colours the apps wrote with it, which matched sRGB (0309).

Conclusion#

Field 12 of a colour message is its colour space: 1 (or absent, or 0) for sRGB and 2 for Display P3, which the apps convert when drawing. Other values seem to fall back to sRGB. The apps write 1 for the colours seen so far; a colour picked in Display P3 would presumably be stored with 2. A reader must check field 12 before treating the components as sRGB.

Evidence#

2021#5 11.1: 0 → 1 says that field 11.1 of the type-2021 record with ID 5 held 0 and holds 1; without an ID, that some record of the type does. = is a value it holds, ≠ one it doesn't, ~ bytes it contains, and ×2 how often a field occurs. These statements were checked against the documents by script (fixtures/evidence.py); only means that nothing else differs but the previews.
