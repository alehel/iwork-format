0086: Chart grouped by column#

App release: 15.4

Status: run

0067 found a chart's data in field 10000.7 of its record (type 5021), but with only one chart, a vertical bar chart grouped by row, the other fields of 10000 couldn't be told apart. This experiment is one of eight (0079–0086) that each change one thing about the chart: here, the grouping.

Setup#

Keynote15.4 (build M15.4-7051.0.79-2)
macOS26.5.2 (25F84)
Date2026-11-09
BaselineExperiment 0067, chart.key (vertical_bar_2d, grouped by row)

Recipe#

mkdir -p samples/0086
osascript recipes/0079-keynote-chart-type.applescript "$PWD/samples/0086/vertical_bar_2d-column.key" vertical_bar_2d column

The recipe adds the same 2 × 3 chart as 0067 to slide 1, with the type vertical_bar_2d, grouped by chart column.

Observation#

Compared with 0067's chart grouped by row, field 10000.5 is 2 here and 1 there. Everything else is unchanged, including field 10000.1 (1, vertical bar) and the data grid in 10000.7. The rows are still r1 and r2, the columns a, b and c, and the values {1, 2, 3} and {4, 5, 6}.

Conclusion#

Field 10000.5 of a chart is how its data is grouped into series: 1 by row, 2 by column. The data grid is stored the same way either way, as rows of values with row and column names. So a reader builds the series from the grid's rows when 10000.5 is 1, and from its columns when it is 2.

Evidence#

2021#5 11.1: 0 → 1 says that field 11.1 of the type-2021 record with ID 5 held 0 and holds 1; without an ID, that some record of the type does. = is a value it holds, ≠ one it doesn't, ~ bytes it contains, and ×2 how often a field occurs. These statements were checked against the documents by script (fixtures/evidence.py); only means that nothing else differs but the previews. What the app showed, and what follows from it, is the experiment's own.
